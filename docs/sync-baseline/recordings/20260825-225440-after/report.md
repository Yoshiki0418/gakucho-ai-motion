# 同期評価レポート — after(フェーズ0 適用後)

- 収録日: 2026-08-25
- 比較対象: `../20260825-222424-before/`
- 構成: dev フロントエンド(:4000) → **改修版バックエンド(:8091)** → T2M(:8100)
- アバター: `gakucho_v3_suit.glb`
- モーション生成モデルは変更していない(Custom-T2M-Lab のまま)

## 結果

| 指標 | before | after | |
| --- | --- | --- | --- |
| **担当発話の開始からのズレ(中央値)** | −111 ms | **+76 ms** | 符号が反転し自然な方向へ |
| **担当発話の開始からのズレ(最大)** | **556 ms** | **82 ms** | **6.8 倍の改善** |
| **発話が始まる前に発火した回数** | **3 / 5** | **0 / 5** | 解消 |
| 発話が終わってから発火した回数 | 0 | 0 | — |
| スケジュール時刻からの遅れ | (概念なし) | +21〜82 ms | 予定どおりに発火 |

改修前は 5 回中 3 回が「喋り出す前にジェスチャが終わりかけている」状態だった。
改修後は**すべてのモーションが担当発話の再生中に収まっている**(`再生中=#1` `#2` `#3`)。

残る +76 ms は、React の状態更新 1 フレームぶんと BVH のパース時間(約 30 ms)。
人が音と動きのズレを感じ始めるのは概ね 100 ms 以上とされるため、実用上は十分。

## 何を変えたか

### バックエンド

1. **TTS が発話長を返すようにした** — `synthesize_with_duration()` を追加。
   Style-Bert-VITS2 は波形を持っているのでサンプル数から直接算出する。
2. **発話に通し番号を振った** — `audio_chunk` に `segment_id` / `duration_ms` を追加。
3. **モーションを発話に紐付けた** — `MotionJobChannel` に発話カウンタを持たせ、
   `generate_motion` ツールが呼ばれた時点の「次に喋る文」の番号を記録する。
   `motion_chunk` に `segment_id` / `start_offset_ms` として載せる。

### フロントエンド

4. **モーションを届いた瞬間に再生しなくした** — `segment_id` で指定された発話が
   AudioContext 上のいつ鳴るかが確定してから、その時刻にスケジュールする。
   モーションは発話より先に届くのが普通なので、届いた分は保留しておく。
5. **時計を音声に一本化した** — `BvhViewer` のミキサー駆動を `THREE.Clock` から
   `AudioContext.currentTime` へ変更。従来は 2 つの時計で走っていたため、
   同時に始めても必ずドリフトしていた。
6. **モーションの尺を発話に寄せた** — `timeScale = clip長 / 発話長`。
   極端な変速は不自然なので 0.7〜1.5 倍に制限。
7. **取りこぼし対策** — 対応する発話が最後まで来なかったモーションは応答完了時に即時再生。
   ただし `done` は音声デコードの完了前に届くので、デコード中は判断を保留する。

## フェーズ0 で解決しなかったこと

意図的に手を付けていない。いずれもモーション生成側の課題で、フェーズ1(SentiAvatar 検討)の対象。

1. **長い応答でモーションが出ない** — `02-long-explanation` は 46 秒の発話に対して 0 回。
   エージェントがツールを呼ばない限り何も起きない構造は変わっていない。
   co-speech gesture そのものが無いため。
2. **1 発話に 1 モーションの上限** — `03-multiple-actions` は「お辞儀してから座る」の
   指示に対して依然 1 つしか出ない。スケジュール機構は複数モーションに対応済みなので、
   エージェント側が複数回ツールを呼べば動く。
3. **発話中の無動作区間** — モーションが終わった後の残り発話は idle のまま。
